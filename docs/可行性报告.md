# 用自建 WebView 把 G2 接上 ChatGPT

**结论：技术上可行，但只有非官方路线能同时满足全部要求。** 在 Android 上可以这样做：写一个原生 Kotlin App，内嵌系统 `android.webkit.WebView`（备选 Mozilla GeckoView），只用来登录 chatgpt.com。G2 的麦克风音频由 Even 官方 App 里的一个 Even Hub 插件采集（16 kHz PCM），通过本机 `127.0.0.1` WebSocket 交给这个 App。App 在页面加载时注入脚本，替换 `navigator.mediaDevices.getUserMedia`，把眼镜音频当成麦克风输入，交给 ChatGPT 网页自带的听写（dictation）识别。回复从页面 DOM 读出，回传给插件，用 `textContainerUpgrade` 显示在眼镜上。Electron 不能在 Android 上运行；Capacitor、Tauri 这类外壳底层用的还是同一个系统 WebView。所以用户设想的"Electron 方案"，在 Android 上的实际对应就是这个原生 WebView App。官方路线里，没有一条能同时做到四件事：用 G2 麦克风、用 ChatGPT 自己的语音识别、走用户自己的账号并留在历史里、把文字送回眼镜。Sign in with ChatGPT 明确不支持音频输入和转写 API；ChatGPT Android App 也没有把回复交还给其他 App 的接口。这个方案有三个代价。第一，用 Google 注册的账号无法在 WebView 里登录。第二，两个 App 在后台和锁屏时都要保活，需要前台服务和手机厂商的白名单设置。第三，也是最重的：这种做法属于 OpenAI 使用条款明文禁止的"程序化提取输出"，风险落在用户的主账号上，工程手段消除不了。建议先在手机上依次验证三件事：WebView 能否登录、合成麦克风能否触发听写、回复能否可靠读出。其中任何一项失败，整个方案都要改道。

## 没有一条路线同时满足全部五个条件

把需求拆开，一共五个条件：音频来自 G2 麦克风；用 ChatGPT 自己的语音识别；走用户自己的 ChatGPT 账号并进入历史；回复文字显示在眼镜上；OpenAI 和 Even 官方允许这种做法。下表把调研到的七条路线逐条对照。

| 路线 | G2 麦克风 | ChatGPT 自家识别 | 自己账号与历史 | 文字回眼镜 | 官方允许 |
|---|---|---|---|---|---|
| A. 独立 WebView App 驱动 chatgpt.com（推荐） | 是，经 Even 插件 | 是，网页听写 | 是 | 是 | 否，违反使用条款 |
| B. 无障碍服务操控 ChatGPT 官方 App | 否，只能用手机麦克风 | 是 | 是 | 是 | 否 |
| C. ChatGPT App 语音 + 自建 MCP 工具推送到眼镜 | 否，只能用手机或耳机麦克风 | 是 | 是 | 是，但由模型决定是否调用 | 机制允许，套餐资格不明 |
| D. Sign in with ChatGPT 套餐额度 | 是 | 否，不支持音频 | 用套餐额度，不进历史 | 是 | 是，有资格限制 |
| E. Even AI 的 Agent Configure 指向自建端点 | 是 | 否，由 Even 识别 | 否 | 是 | 是 |
| F. OpenAI API | 是 | 同厂商模型，未证实与听写相同 | 否，按量另付 | 是 | 是 |
| G. Mac 常开 Chrome 做中继 | 是 | 是 | 是 | 是 | 否 |

官方路线里最接近需求的是 D，Sign in with ChatGPT（SIWC）。它是一个 OAuth/PKCE 流程，第三方应用可以用用户的套餐额度调用 `POST https://api.openai.com/v1/responses` ([SIWC 开源应用文档](https://developers.openai.com/siwc/token-sharing-open-source))。但预览限制写明：**不支持音频和视频输入，不支持转写 API，请求必须带 `store: false`** ([SIWC preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations))。文档还说明，这个流程不能访问用户的 ChatGPT 对话 ([SIWC 开源应用文档](https://developers.openai.com/siwc/token-sharing-open-source))。所以 SIWC 只能承担"文字进、文字出"这半程，识别得另找方案，对话也不会出现在 ChatGPT 历史里（这一点是根据 `store: false` 推断的，官方没有直接说明）。按二手资料，在商业应用里使用套餐额度只限 Plus 和 Pro，商业或托管应用目前只开放给申请试用的合作伙伴，开源和本地运行的应用可以直接接入 ([eesel.ai 摘要](https://www.eesel.ai/blog/sign-in-with-chatgpt))。个人自用的 App 大概率属于后一类。

ChatGPT Android App 有三个官方入口：设为系统默认数字助理、快捷设置磁贴、桌面"语音"快捷方式。三者都只是唤起 ChatGPT 的语音界面 ([9to5Google](https://9to5google.com/2025/03/14/chatgpt-default-assistant-android/); [9to5Google 磁贴](https://9to5google.com/2024/01/23/chatgpt-android-quick-settings-shortcut/))。调研没有找到任何能传入音频或文字、再取回回复的 intent 或 deep link；社区至今还在请求官方提供深链接 ([OpenAI Community](https://community.openai.com/t/feature-request-deep-linking-for-projects-and-shortcuts/1248167))。这些入口从系统音频输入录音，而 G2 **没有扬声器，只通过蓝牙低功耗（BLE）和手机相连** ([Even Hub 概览](https://hub.evenrealities.com/docs/get-started/overview))。没有资料表明 G2 会以蓝牙耳机麦克风的身份出现在系统里；连 Even 自家的 Even AI 都不能切换音频输入源 ([Even 支持文章](https://support.evenrealities.com/hc/en-us/articles/17206473148815-G2-Glasses-and-Even-Realities-App-Fail-to-Transcribe-or-Display-Content-Correctly-When-Voice-Input-Is-Set-to-Glasses))。因此 B 和 C 两条路线，用户只能对着手机或蓝牙耳机说话。

C 路线值得单独说明。做法是在 ChatGPT 里添加一个自建的 MCP 服务器 ([Apps SDK 连接文档](https://developers.openai.com/apps-sdk/deploy/connect-chatgpt))，指示模型每次回答时调用 `push_to_glasses(text)`，把答案作为参数传过去，服务器再把文字转发到眼镜。这条路线保留了 ChatGPT 自己的识别和历史，用的也是官方提供的机制，是几条路线里最合规的。但它有两个不确定点。一是开发者模式的套餐资格，资料互相矛盾：帮助中心的片段说只限 Business、Enterprise、Edu，开发者文档却说所有套餐都可用；而且写操作默认需要用户确认 ([VentureBeat](https://venturebeat.com/dev/openai-adds-powerful-but-dangerous-support-for-mcp-in-chatgpt-dev-mode); [OpenAI 帮助中心片段](https://help.openai.com/en/articles/12584461-developer-mode-and-full-mcp-connectors-in-chatgpt))。二是语音模式下工具会不会被调用，目前没有验证。

E 路线：Even App 里有"Settings → Even AI → Agent Configure"，可以把 Even AI 指向任何兼容 `/v1/chat/completions` 格式的 URL ([evenai-anthropic-bridge](https://github.com/jase-perf/evenai-anthropic-bridge))。不写代码就能把眼镜问答接到自己的后端。但识别由 Even 完成；Even 官网还注明，ChatGPT 集成只限 G1 ([Even AI 眼镜页](https://www.evenrealities.com/ai-glasses))。F 路线 OpenAI API 在技术上最稳。转写模型 `gpt-transcribe` 每分钟 $0.0045，`gpt-live-transcribe` 每分钟 $0.017 ([OpenAI 定价](https://developers.openai.com/api/docs/pricing))。Realtime 接口的 PCM 输入只接受 24 kHz，G2 的 16 kHz 音频需要先重采样 ([client_secrets 参考](https://developers.openai.com/api/reference/resources/realtime/subresources/client_secrets/methods/create))。但 API 按量计费，和 ChatGPT 订阅、历史完全分开，用户已经明确排除。

B 路线：无障碍服务确实能读写 Jetpack Compose 界面的语义树 ([Deque](https://www.deque.com/blog/building-accessible-android-apps-with-jetpack-compose-how-accessibility-service-interacts-with-jetpack-compose/))，文字进、文字出都做得到。但 Android 没有虚拟麦克风接口，不 root 就没法把眼镜音频送进 ChatGPT App（这是推断）。Google Play 政策把自动化工具和助手排除在"无障碍工具"之外 ([Play Console 帮助](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en))；侧载安装的版本在 Android 13 及以上，还要用户手动开启"受限设置" ([CleanBrowsing](https://cleanbrowsing.org/support/mobile/disable-restricted-settings-android))。G 路线最稳，但需要一台常开的 Mac，不符合"只用 Android"的前提；它可以用作开发注入脚本的试验台。在只用 Android 的前提下，同时满足前四个条件的只剩 A。

## Electron 在 Android 上的替身是原生 WebView 或 GeckoView

Electron 只发布 macOS、Windows、Linux 三个平台的二进制 ([Electron README](https://github.com/electron/electron#platform-support))。Capacitor、Cordova、React Native WebView、Tauri 2 移动端都用系统 WebView 渲染 ([codercops](https://blog.codercops.com/blog/tauri-2-desktop-mobile-apps-rust-web-2026))。Tauri 在 Android 上注入初始化脚本的做法，只对它自己协议下的页面有效，对 chatgpt.com 这样的外部站点无效 ([tauri-runtime 源码](https://docs.rs/tauri-runtime/2.7.1/src/tauri_runtime/webview.rs.html))。也就是说，外壳框架不会带来额外能力，往远程站点注入脚本仍然要靠原生 API。真正能选的引擎只有三种。

第一种是系统 WebView，直接用 Kotlin 写。androidx.webkit 从 1.9.0 起提供 `WebViewCompat.addDocumentStartJavaScript`：对符合来源规则的每个页面，在文档开始加载时运行脚本，需要在 `loadUrl` 之前注册 ([WebViewCompat](https://developer.android.com/reference/androidx/webkit/WebViewCompat))。替换 `getUserMedia` 需要的正是这个时机。第二种是 GeckoView，即完整的 Firefox 引擎。它可以把 WebExtension 打包进 APK，用内容脚本注入页面，并和原生代码互相发消息 ([GeckoView 提交](https://github.com/mozilla/geckoview/commit/e54fd397c3be6ea6ec88529c2c6b14597c0e48a2))；麦克风权限由 App 在 `onMediaPermissionRequest` 中自行处理 ([GeckoView 权限文档](https://firefox-source-docs.mozilla.org/mobile/android/geckoview/consumer/permissions.html))。第三种是 Chrome Custom Tabs，登录体验最好，但嵌入它的 App **拿不到 DOM，也不能注入脚本** ([Chromium Custom Tabs FAQ](https://chromium.googlesource.com/chromium/src/+/main/docs/security/custom-tabs-faq.md))，对本项目没有用处。

选哪种引擎，主要由登录方式决定。从 2021 年起，Google 拒绝来自 `android.webkit.WebView` 的 OAuth 请求（报 `disallowed_useragent` 错误），2023 年 2 月起全面执行 ([Google Developers Blog](https://developers.googleblog.com/2021/06/upcoming-security-changes-to-googles-oauth-2.0-authorization-endpoint.html))；CEF 等嵌入式浏览器框架也被屏蔽 ([Google Security Blog](https://security.googleblog.com/2019/04/better-protection-against-man-in-middle.html))。2026 年有一个 chatgpt.com 的 WebView 封装项目，README 写明不支持 Google 登录，邮箱、手机号、Apple 登录留给用户自己测试 ([chatgpt-webview-android](https://github.com/Duanzhoutao/chatgpt-webview-android))。WebView 里用 Passkey，需要 App 和站点之间做 Digital Asset Links 关联 ([Android 凭据管理文档](https://developer.android.com/identity/sign-in/credential-manager-webview))，第三方 App 无法为 chatgpt.com 建立这种关联，所以等于不可用。结论是：**用户的 ChatGPT 账号如果能用邮箱加密码或邮箱验证码登录，就用系统 WebView；如果只能用 Google 登录，就改试 GeckoView。** GeckoView 发出的 UA 是 Firefox for Android，Google 登录有可能通过，但没有找到 2026 年的实测资料。伪造 UA 绕过 Google 检测，是有人用过的老办法 ([react-native-oauth PR](https://github.com/fullstackreact/react-native-oauth/pull/228))。但这等于规避 Google 的安全控制，不应该作为设计前提。

## 推荐架构：Even 插件负责采音，独立 App 驱动网页听写

第一版由两个组件构成，中间用一条本机 WebSocket 连接。

**眼镜一侧是一个 Even Hub 插件**，运行在 Even App 内置的 Chromium WebView 里 ([Even Hub Networking](https://hub.evenrealities.com/docs/build/networking))。插件申请 `g2-microphone` 和 `network` 两项权限 ([Packaging](https://hub.evenrealities.com/docs/ship/packaging))，用 `audioControl` 拿到 G2 四麦阵列输出的单路 16 kHz s16le 单声道 PCM ([Device APIs](https://hub.evenrealities.com/docs/build/device-apis))，再推给本机 WebSocket。交互用镜腿或 R1 戒指的长按和松开 ([Even Hub 概览](https://hub.evenrealities.com/docs/get-started/overview))，实现"按住说话"：按下开始听写，松开停止并发送。SDK 没有打开 URL、发 intent 或跨 App 通信的方法 ([Even Hub FAQ](https://hub.evenrealities.com/docs/reference/faq))，网络是插件和外界交换数据的唯一通道。打包发布后的插件只能访问 `network.whitelist` 里列出的完整来源。Even App 在请求离开 WebView 之前就会拦截白名单以外的请求，CORS 也照常生效 ([Networking](https://hub.evenrealities.com/docs/build/networking))；WebSocket 适用同样的白名单规则 ([FAQ](https://hub.evenrealities.com/docs/reference/faq))。白名单是否接受 `ws://127.0.0.1:8765` 这样的条目，文档没有写，必须实测。如果不接受，退路是自己控制的 HTTPS/WSS 中继服务器，这是文档明确支持的模式。

**手机一侧是独立 App**，由三部分组成。第一部分是跑在前台服务里的本地 WebSocket 服务器。社区项目 droidbridge 就是这样做的：用 NanoHTTPD/NanoWSD 在 8765 端口提供 HTTP 和 WS，靠带常驻通知的前台服务保活 ([droidbridge](https://github.com/Commute773/droidbridge))。第二部分是登录 chatgpt.com 的 WebView，以及页面加载时注入的脚本。脚本把 `getUserMedia` 替换为返回 WebAudio `MediaStreamDestination` 流的函数，这是模拟麦克风的成熟做法 ([WebRTC.ventures](https://webrtc.ventures/?p=7687))。原生层通过 `WebMessagePort` 把 PCM 送进页面，再由 AudioWorklet 从 16 kHz 重采样到 AudioContext 的采样率。WebView 的麦克风请求在 `WebChromeClient#onPermissionRequest` 中处理，只授予 `RESOURCE_AUDIO_CAPTURE` ([PermissionRequest](https://d.android.com/reference/android/webkit/PermissionRequest))。有项目发现，还需要申请 `RECORD_AUDIO` 和 `MODIFY_AUDIO_SETTINGS` 运行时权限，否则音频管线会出错 ([hotwire-native-android PR 199](https://github.com/hotwired/hotwire-native-android/pull/199))。第三部分负责读取回复。主方案是用 MutationObserver 监听最后一条助手消息，把新增文字通过 JS 到原生的桥接送出。判断回复结束看三个信号：停止按钮变回发送按钮，复制等操作按钮出现，文字连续若干毫秒不再变化。备选方案是在页面加载时包装 `window.fetch`，旁路读取 `backend-api/conversation` 的 SSE 流；数据更结构化，但依赖未公开的内部协议。

**为什么用听写，而不是高级语音模式。** ChatGPT 网页的听写是先录一段音，返回一段可编辑的转写文字，再由用户发送 ([chatai.guide](https://chatai.guide/features/chatgpt-whisper/))。这正好对应"按住说话"，发出的是普通文字消息，回复也是文字。高级语音模式走 LiveKit 的 WebRTC 通道 ([LiveKit 博客](https://livekit.com/blog/openai-livekit-partnership-advanced-voice-realtime-api))，回复以语音为主，文字得从字幕里取，更容易出问题；移动浏览器的 UA 下是否提供高级语音也不清楚。需要强调的是：**调研没有找到任何公开项目把外部音频注入过 ChatGPT 网页听写**。这是整个方案最大的技术未知数。页面可以通过 `track.label`、`enumerateDevices()` 等接口识别出合成音轨，chatgpt.com 是否做了这类检查，目前不得而知。

**显示一侧**，`createStartUpPageContainer` 和 `rebuildPageContainer` 的文字上限是 1,000 字符；`textContainerUpgrade` 的上限是 2,000 字符，更新时不闪烁。全屏大约能放 400 到 500 个字符，超出部分在事件捕获容器里由固件负责滚动 ([Display](https://hub.evenrealities.com/docs/build/display))。眼镜只有一套固件字体，字体里没有的字形会被直接丢弃 ([Display](https://hub.evenrealities.com/docs/build/display))；FAQ 把中文列为支持语言 ([FAQ](https://hub.evenrealities.com/docs/reference/faq))。如果上限其实按 UTF-8 字节计算，一个汉字占 3 字节。实测之前，保守按每屏约 300 字、每次更新约 660 字做预算。

还有一种形态更贴近用户的原始设想，即"一个 App 同时管 chatgpt.com 和 G2"：App 绕过 Even App，直接通过 BLE 连接 G2。Mentra 的 Bluetooth SDK（Apache-2.0 许可，包含 Android Kotlin 版）把 Even Realities 列为兼容设备，显示文字的示例点名了 G2 ([Mentra SDK](https://github.com/Mentra-Community/Mentra-Bluetooth-SDK-Starter-Kit))；MentraOS 也宣布完整支持 G2 ([MoguraVR](https://www.moguravr.com/https-www-moguravr-com-mentraos-even-realities-g2/))。社区逆向出来的 G2 协议已经能完成连接、认证和文字显示，但没有记录麦克风音频流的格式 ([even-g2-protocol](https://github.com/i-soxi/even-g2-protocol))。这种形态少一个 App，也少一条本机连接，但代价同样明显：协议不是官方的，固件一更新就可能失效；而且 G2 很可能同一时间只接受一个中心设备连接，需要先断开 Even App（这是推断）。建议放到第二阶段，第一版跑通后再评估。

## 账号风险是工程手段消除不了的一项

四类风险中，技术脆弱性、后台保活和登录都有缓解办法，使用条款带来的账号风险没有。

**使用条款与账号。** OpenAI 2024-12-11 版使用条款禁止 "Automatically or programmatically extract data or Output"，也禁止绕过限流或保护措施，违反者可能被暂停或终止账号 ([OpenAI ToU 2024-12-11 镜像](https://open.windriver.com/info/uni-license-list/licenses/openai-tou-20241211.html); [openai.com 修订版](https://openai.com/policies/row-terms-of-use/revisions/2024-12-11/))。SIWC 文档也明确要求不要把它的流程指向 ChatGPT 的 `backend-api` ([SIWC models-and-inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference))。用程序读取自己的回复、显示到眼镜上，按字面已经属于第一条禁止事项；合成麦克风和伪造 UA 则更接近第二条。2026 年现行条款的页面抓取被拒，措辞有没有变化，没有核实。

对用户有利的一点是：脚本跑在真实登录的页面里，sentinel、工作量证明和 Turnstile 令牌都由页面自己计算，网络流量和正常使用看不出区别。相比之下，独立的逆向客户端在 2023 到 2024 年 OpenAI 加上这些校验之后，纷纷停止维护并归档 ([acheong08/ChatGPT](https://github.com/acheong08/ChatGPT))。但行为特征仍可能暴露：全天在线、对话轮次密集、使用合成音轨。一个老牌逆向项目警告，自动化操作被封号的概率很高，并建议用小号 ([node-chatgpt-api](https://github.com/josStorer/node-chatgpt-api))；而论坛上的封号案例中，没有一例被明确归因于界面自动化 ([OpenAI Community](https://community.openai.com/t/sudden-openai-account-ban-with-no-explanation-lost-access-to-custom-gpts-and-business-workflows/1381965))。换句话说，封号概率没有可靠数据，可一旦发生，损失的是用户的主账号、全部历史和订阅。能做的只有尽量减少异常特征：只在用户按住说话时工作，不做全天自动对话，不伪造 UA，不并发请求。

**登录。** 除了上面说的 Google 限制，chatgpt.com 在 OpenAI 自家的 Agent 浏览器和 Windows 客户端上都出现过"验证你是人类"的无限循环 ([OpenAI Community](https://community.openai.com/t/chatgpt-agent-not-passing-cloudflare-verification-for-chatgpt-com/1336765))；基于 WebView 的浏览器也报告过 Cloudflare 验证循环 ([Privacy Browser 问题](https://redmine.stoutner.com/issues/1053))。所以要预期定期重新登录，偶尔还要人工点过 Turnstile 验证。App 必须能随时把 WebView 切到前台让用户处理。

**后台与锁屏。** 两个 App 都要保活。Even 插件这边，官方文档自相矛盾。生命周期页面说，Android 内存紧张时插件 WebView 可能被挂起，甚至被回收；挂起后 `audioControl` 的采音会停止，回到前台后要重新开启 ([Background & Lifecycle](https://hub.evenrealities.com/docs/build/background-lifecycle))。FAQ 却说后台根本不能发网络请求 ([FAQ](https://hub.evenrealities.com/docs/reference/faq))。Even 客服建议，在 Android 上把 Even App 锁定在后台，并开启"允许后台使用" ([Even 支持：频繁断连](https://support.evenrealities.com/hc/en-us/articles/17123822627727-G2-Glasses-Frequently-Disconnect-from-the-Even-Realities-App))。

独立 App 这边需要一个带常驻通知的前台服务，类型的选择有讲究。不要用 `microphone` 类型，Android 14 及以上禁止从后台启动这种前台服务 ([前台服务后台启动限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start))；也不要用 `dataSync`，Android 15 及以上每 24 小时只允许运行 6 小时 ([前台服务超时](https://developer.android.com/develop/background-work/services/fg-service-timeout))。个人侧载的 App 用 `specialUse` 或 `connectedDevice` 比较合适（这是推断）。WebView 本身也有陷阱：`onPause()` 不会停止 JS，但 `pauseTimers()` 会冻结整个进程里所有 WebView 的计时器 ([plateaukao 博客](https://plateaukao.github.io/blog/posts/differences-between-onpause-and-pausetimers-for-android-webview/))；隐藏的 WebView 如果允许降低渲染优先级，它的渲染进程会成为内存不足时优先回收的对象 ([Managing WebView](https://developer.android.com/guide/webapps/managing-webview))。dontkillmyapp.com 把华为、小米、一加、三星列为后台查杀最激进的厂商 ([dontkillmyapp](https://dontkillmyapp.com/))。用户需要手动把电池设置改为"不受限制"，打开自启动，并在最近任务里锁定 App。熄屏后 WebView 的计时器会不会被节流，没有文档说明，只能实测。

**技术脆弱性。** chatgpt.com 的按钮、选择器和听写流程都没有公开文档，每次前端发版都可能变化。输入框是 React 受控组件或富文本编辑器，直接改 `.value` 不起作用，要用 `execCommand('insertText')` 或派发 `input` 事件。这是持续性的维护成本。所有选择器应集中放在一份可以远程更新的配置里。

## 先在手机上跑七个验证实验

实验按"失败后影响有多大"排序。前三项任何一项失败，A 路线都要大改；后四项决定体验和稳定性。前三项不需要眼镜。第二、三项可以先在 Mac 的 Chrome 里用同一段注入脚本调好，再移到 Android。抓取的 Logcat、录屏和样本音频不放进仓库。

| 顺序 | 实验 | 做法 | 通过标准 | 失败后怎么办 |
|---|---|---|---|---|
| 1 | WebView 登录 | 先在 chatgpt.com 的账号设置里确认登录方式。做一个最小的 Kotlin WebView App（可参考 chatgpt-webview-android），登录后杀掉进程再打开 | 登录成功；重启后会话还在；移动版页面上有听写按钮 | 换 GeckoView 重试；仍失败则 A 路线不成立 |
| 2 | 合成麦克风听写 | 用 `addDocumentStartJavaScript` 替换 `getUserMedia`，通过 AudioWorklet 喂入一段 16 kHz 中文录音，由脚本点击听写的开始和停止 | 输入框出现正确的中文转写；记录是否必须授予 `RECORD_AUDIO` | 页面拒收合成音轨，说明核心假设不成立，退到 C 或 D |
| 3 | 回复读取与结束判定 | 用 MutationObserver 把新增文字推到 Logcat，同时对比旁路读取 SSE 的效果 | 连续 20 轮回复完整、没有截断，结束判定不出错 | 改用旁路 SSE，或改用"文字 N 毫秒不变"判定 |
| 4 | G2 音频送到本机 | 用开发者模式扫码加载插件，`audioControl` 采到的音频推到 App 的 `ws://127.0.0.1:8765`；再用 `evenhub pack` 测试白名单能否写入这个地址 | 音频帧连续到达并记下帧长；打包工具接受这个来源 | 改用自己控制的 HTTPS/WSS 中继 |
| 5 | 眼镜显示中文 | 用 `textContainerUpgrade` 推送长篇中文回复，测试翻页 | 不丢字；弄清上限按字符还是按字节计算 | 调整分页预算 |
| 6 | 端到端与锁屏 | 把两个 App 串起来，开启前台服务并把电池设为不受限制；锁屏 1、5、15 分钟后再按住说话 | 锁屏 15 分钟后仍能完成一轮对话；记录端到端延迟 | 要求使用时保持亮屏，或继续研究保活办法 |
| 7 | 蓝牙麦克风与直连 | 在系统蓝牙设置里看 G2 是否显示为音频设备；用 `adb shell dumpsys package com.openai.chatgpt` 查 ChatGPT App 导出的 intent；试用 Mentra SDK，看能否拿到 G2 麦克风音频 | 判断 B、C 路线能不能用上 G2 麦克风，单 App 直连是否可行 | 维持两个 App 的架构 |

第 7 项成本最低，可以和前几项并行做。如果 G2 意外能作为系统蓝牙麦克风使用，C 路线就会变成一个合规的完整方案。

## 结论

真正的瓶颈不在工程，而在需求本身。"ChatGPT 自己的识别加上用户自己的账号"这个组合，只能通过 OpenAI 明令禁止的方式实现。只要放宽一个条件，就有官方允许的路线可走。如果不坚持"对着 G2 说话"，C 路线（ChatGPT App 语音加自建 MCP 推送）保留了识别和历史，用的也是官方机制。如果不坚持"用 ChatGPT 的识别并进入历史"，D 路线（SIWC 套餐额度加其他识别）也合规，而且花的是已经付费的订阅额度。所以第一版的眼镜端插件和显示层要设计成与文字来源无关：如果哪天账号风险成真，或者 chatgpt.com 的改版让注入失效，可以切换到 C 或 D，不必重写眼镜端。

整个方案能否成立，取决于第 2 项实验：chatgpt.com 的听写会不会接受一条合成音轨。这件事在 Mac 的 Chrome 上一天之内就能验证。应该先花这一天，再决定是否投入 Android 工程。

## 实验记录

### 实验 2：合成麦克风听写（2026-11-07，通过）

在 Mac 的 Chrome 157 上，用一个未打包扩展在 chatgpt.com 加载的最开始（`document_start`，页面自己的脚本环境）替换掉 `getUserMedia`。网页要麦克风时，拿到的是一段 7.02 秒的中文 TTS 样本，按 16 kHz、每帧 100 ms 的方式送入，和 G2 插件的格式一致。点击听写后，网页返回的转写是"今天下午三点在会议室讨论眼镜项目的进度请准备好上周的测试数据。"，和原文逐字一致，只少了中间的一个逗号。

日志里看到的网页行为：

- 网页先调用 `enumerateDevices`（返回 5 个设备），再调用 `getUserMedia`，请求的约束是 `{"channelCount":1,"sampleRate":4000,"deviceId":{"exact":"default"}}`。合成音轨不满足这些约束，网页照样接受了。
- 录音用 `MediaRecorder` 的默认格式 `audio/webm;codecs=opus`。
- 停止听写后，网页调用 `track.stop()`，再把录音 `POST` 到 `/backend-api/transcribe`，772 ms 后返回 200。
- 音轨的 label 是 `MediaStreamAudioDestinationNode`，网页没有因此拒收。

结论：核心假设成立。ChatGPT 网页的听写会接受外部注入的音频，并用它自己的识别返回正确的中文转写。还没有验证的是：安卓 WebView 里的表现（实验 1）、回复读取（实验 3）、英文样本，以及更长或带噪声的真实语音。

### 实验 3：回复读取与结束判定（2026-11-07，DOM 读取通过，数据流解析待复测）

在 Mac 的 Chrome 上，通过 Claude in Chrome 在用户的 chatgpt.com 会话里发了两条测试消息，扩展只做被动读取。

**chatgpt.com 已改版。** 页面上已经没有 `data-testid` 和 `data-message-author-role`，原先预设的选择器全部失效。2026-11-07 的结构是：

| 用途 | 选择器 |
|---|---|
| 助手消息 | `[data-content-search-unit-key$=":assistant"]` |
| 回复正文 | `[data-markdown-text-style="assistant-message"]` |
| 用户消息 | `[data-content-search-unit-key$=":user"]` |
| 回合状态 | `[data-talvt-turn-state]`，值为 `in_progress` → `complete` |
| 停止按钮 | `button[aria-label="Stop"]`（只有英文界面下是这个标签） |
| 复制按钮 | `button[aria-label="Copy"]` |

第二条消息（"列出五个提高专注力的方法"）的时间线，从按下发送算起：

| 时间 | 事件 |
|---|---|
| 0 s | 出现 Stop 按钮 |
| +5.5 s | 第一批文字出现 |
| 约 +9.3 s | 文字不再变化（407 字符，1111 UTF-8 字节） |
| +13.4 s | 回合状态变为 `complete`，同一刻 Stop 按钮消失、Copy 按钮出现 |
| +14.2 s | 页面主动中断对话数据流（`AbortError`） |

结论：从 DOM 读取完整回复是可靠的，`data-talvt-turn-state="complete"` 是最直接的结束信号。文字定稿之后大约还要 4 秒，这个状态才会变成 `complete`。所以眼镜端应该边生成边显示，不要等结束信号。"文字 1.5 秒不变"会在生成中途的停顿里误报，不能单独用来判断结束。

对话数据流的格式是一种未公开的增量编码（`"v1"`）：每个事件是 `{p, o, v}` 操作，缺省的 `p`/`o` 沿用上一个事件，`patch` 里装着一组操作。回复正文只出现在 `/message/content/parts/N` 的 `append` 操作里。`/message/metadata/model_dil_v2/fallbackMarkdown` 会把同样的文字再追加一遍，最初的解析没有排除它，结果文字被重复计算（279 对 141 字符，862 对 407 字符）。修正后的解析器在仿照真实格式的本地模拟页上结果完全一致，但还没有在 chatgpt.com 上复测。界面标签是英文的，换成中文界面后 `aria-label` 会变。

### 实验 1（Firefox 安卓版）及实验 2、3 的手机复测（2026-11-07，通过）

改走 GeckoView 路线后，先用 Firefox for Android 159 代替自建 App。Firefox 安卓版本身就是 GeckoView 做的。手机是三星 Galaxy Z Fold5。测试扩展用 `web-ext run -t firefox-android` 通过 USB 临时装入，脚本和 Chrome 版是同一份，只换了 manifest。Firefox 的 MV3 也支持 `world: "MAIN"`，在 chatgpt.com 的 nonce CSP 下注入成功。

**登录**：邮箱加密码登录成功。还没测杀进程后会话是否保留，也没确认是否出现过"验证你是人类"的检查。

**听写**：和 Mac 上的结果一致，转写逐字正确。差别在细节上：

- `enumerateDevices` 返回 2 个设备；`getUserMedia` 的约束是 `{"audio":{"channelCount":1,"sampleRate":4000}}`，不带 `deviceId`。
- 录音格式是 `audio/ogg; codecs=opus`。
- `/backend-api/transcribe` 795 ms 后返回 200。

**回复读取**：手机上发了一条触发网页搜索的消息，回复 2268 个字符，DOM 读取完整。时间线从按下发送算起：

| 时间 | 事件 |
|---|---|
| +1.17 s | 回合状态变为 `in_progress` |
| +23.76 s | 回合状态变为 `complete` |
| +24.24 s | 页面主动中断对话数据流 |

发现两个问题：

1. **中文界面下按钮标签是中文**："停止""复制"。旧版只认英文的 Stop/Copy，所以没有判定结束。0.3.2 版改为以 `data-talvt-turn-state="complete"` 为准，300 ms 内文字不再变化就判定结束，不依赖按钮标签；同时补上了中文标签作为备用信号。本地模拟页回归通过。手机上的复测见下文。
2. **数据流解析在复杂回复上仍然重复**：重建出 6612 个字符，DOM 实际是 2268 个。带搜索的回复里还有别的路径在追加文字，没有继续排查。正文以 DOM 为准，数据流只作为旁证，这个问题不影响主路线。

**0.3.2 版复测**：在中文界面下又发了一条消息，回复 1434 个字符（3199 UTF-8 字节），里面带一个地图组件。这次正确判定为 `DONE (complete)`：

| 时间 | 事件 |
|---|---|
| +1.96 s | 回合状态变为 `in_progress`，第一批文字出现 |
| +10.9 s | 文字暂停变化，此时只有 703 个字符 |
| +16.14 s | 回合状态变为 `complete`；同一刻"停止"按钮消失、"复制"按钮出现，判定结束 |
| +16.64 s | 页面中断对话数据流 |

生成中途有一次超过 1.5 秒的停顿，停顿时的文字只有最终长度的一半。这再次说明"文字 N 秒不变"不能单独作为结束判定。数据流里的地图组件是 `<MapWidgetV2 …>` 这样的标记，DOM 正文里没有它。眼镜只显示文字，所以以 DOM 为准正合适。

结论：GeckoView 引擎上，登录、合成麦克风听写、DOM 回复读取和结束判定都可行，中文界面下也一样。下一步是实验 4（G2 音频送到本机），或者直接做 GeckoView App 的最小原型。

### 实验 4：G2 音频送到本机（2026-11-07，开发者模式和安装版都通过）

做了一个只用来测试的插件：轻点眼镜开关麦克风，把 `audioControl` 采到的每一帧 PCM 通过 WebSocket 发出去。它同时连两个目标：一个是本机回环地址 `127.0.0.1:8777`，另一个是 Mac 的局域网地址，作为对照。手机上还没有配套 App，所以用 `adb reverse tcp:8777 tcp:8777` 把手机的 `127.0.0.1:8777` 转到 Mac 上的接收程序。对插件来说，这和以后连同一台手机上的 App 是一样的：目标都是手机本机的回环地址。（8765 端口在这台 Mac 上已被别的程序占用，所以改用 8777。）插件用 Even App 的开发者模式扫码加载，眼镜是 G2，手机是 Galaxy Z Fold5，Even App 版本 2.4.0。

| 项 | 结果 |
|---|---|
| 插件运行环境 | Even App 内置的安卓系统 WebView（Chrome 156，UA 带 `; wv`），页面来源 `http://192.168.2.1:5173` |
| HTTP 和 WebSocket 连 `127.0.0.1` | 都成功，页面加载后 0.1–0.2 s 内连上，往返 6 ms |
| 对照：连局域网地址 | 都成功，往返 5–25 ms |
| `audioControl(true, Glasses)` | 返回 `true`，第一帧在 240–420 ms 后到达 |
| 帧格式 | 每帧 1600 字节，等于 16 kHz、16 位单声道的 50 ms。模拟器里是 3200 字节（100 ms），所以代码不能假设帧长 |
| 帧间隔 | 中位数 47 ms，p95 65 ms，最大 69–83 ms；4 秒内收到 82 帧，没有丢帧，也没有积压 |
| 帧附带的元数据 | `source: "glasses"`，`direction` 是 -8 或 -17 这样的整数，`speakerRole: "self"` |
| 录音内容 | 5.45 秒，人声清楚，峰值约 -7 dBFS，有 14 个削顶样本 |

第一次测试时，回环地址连不上（`TypeError: Failed to fetch`，WebSocket 关闭码 1006）。原因是手机 USB 重连过一次，`adb reverse` 跟着失效了。恢复转发后，同一个页面的自动重试马上连上了。所以 Even App 的 WebView 本身不拦截发往回环地址的连接，至少开发者模式下是这样。

**打包工具不检查白名单。** `evenhub pack` 对白名单内容不做任何校验：`ws://127.0.0.1:8777`、`http://127.0.0.1:8777`、`ws://localhost:8777`、局域网地址，连明显不合法的裸 `127.0.0.1:8777` 和通配符 `ws://*:8777` 都照样打包成功。开发者模式又不经过 manifest，所以开发者模式的结果不能代表安装版。

**安装版复测。** 用 `evenhub create` 把测试包作为私有 Draft 上传到 Even 开发者平台（应用 `com.g2codeterminal.audioprobe`，版本 0.1.0）。邀请开发者本人的账号做 beta 测试员，把 0.1.0 指到 beta 频道，然后在 Even App 里手动安装。这个包的白名单只写了 `ws://127.0.0.1:8777` 和 `http://127.0.0.1:8777`，没有写局域网地址。结果：

| 项 | 结果 |
|---|---|
| 安装版页面的来源 | `http://127.0.0.1:35145/`：Even App 自己在手机回环地址上起了一个 HTTP 服务来加载插件，端口是随机的 |
| HTTP 和 WebSocket 连 `127.0.0.1:8777`（在白名单里） | 都成功 |
| HTTP 和 WebSocket 连局域网地址（不在白名单里） | **也都成功** |

所以至少在 Even App 2.4.0 的安卓版上，安装版的白名单没有拦截 `fetch` 和 WebSocket。插件页面本身就在 `http://127.0.0.1` 上，连回环地址属于同一主机，也不会遇到混合内容或私有网络访问的限制。安装版这次没有再开麦克风；采音走的是同一个 `audioControl` 接口，开发者模式下已经验证过。

需要留意的是，文档写明白名单会在运行时强制执行。以后的 Even App 版本可能会补上这项检查，所以正式的包仍然应该把 `ws://127.0.0.1:<端口>` 写进白名单。正式发布还要过审核，审核会不会接受回环地址目前不知道。只给自己用的话，走 beta 频道就够了，不需要公开发布。另外，Even App 自己占用了一个随机的回环端口，配套 App 应该用固定端口，并且启动时检查端口是否被占用。

结论：在 Android 上，"Even 插件采音 → 本机回环 WebSocket → 同一台手机上的 App"这条路是通的，开发者模式和安装版都可以，音频格式和 ChatGPT 网页听写需要的一致。如果以后某个版本开始拦截回环地址，退路是让插件连一个自己控制的 HTTPS/WSS 中继。

### 端到端原型：眼镜说话 → chatgpt.com → 眼镜显示（2026-11-07，前台可用，后台和锁屏失败）

把前面的零件串成完整的一轮。还没有独立 App，用三样东西代替：

- Mac 上的转发程序：眼镜插件和网页都连 `127.0.0.1:8777`，手机通过 `adb reverse` 转到 Mac；
- 手机 Firefox 里的扩展；
- 新的 Even 插件。

插件的操作：轻点开始或结束说话，也可以按住说话、松开发送；上下滑动翻页，双击退出。扩展收到开始指令后点"听写"，把实时音频喂给合成麦克风；收到结束指令后点"停止听写"，等转写出现在输入框里，再点"发送"。回复从 DOM 读取，转成适合眼镜的纯文本后推回插件。

**从 DOM 到眼镜文字的转换。** 眼镜只有一种固件字体，没有粗体、字号和颜色。直接用 `innerText` 会丢掉列表的圆点和编号（它们是 CSS 画的），表格单元格只剩制表符，代码块会带上"复制代码"按钮的文字，KaTeX 公式会出现两遍。所以改成遍历回复的 DOM：

- 标题前加 `■`；
- 列表补回 `•` 和 `1.`，嵌套列表缩进两格；
- 表格每行一条，单元格之间用 ` | `；
- 代码块只保留代码；
- 公式只保留 TeX 源码；
- 按钮、图片和小组件都去掉。

**实现时遇到的几个坑：**

| 问题 | 处理 |
|---|---|
| Firefox 对内容脚本里的 WebSocket 也套用网页的 CSP，连 `ws://127.0.0.1` 报 `NS_ERROR_CONTENT_BLOCKED` | 连接放到扩展的后台脚本里，内容脚本通过 `runtime.connect` 端口转发 |
| MV3 扩展页面的默认 CSP 带 `upgrade-insecure-requests`，后台脚本连 `ws://` 也被拦 | 在 manifest 里把扩展页面的 CSP 设成 `script-src 'self'` |
| 页面环境和隔离环境之间的 `postMessage` 拿到的 `e.source` 不是同一个 window 对象 | 不检查来源，只靠消息前缀区分方向 |
| 浏览器要求页面先有一次真实点击，`AudioContext` 才会运行 | 每次页面加载后在页面上点一下；以后的 App 可以直接允许自动播放 |
| 新回复的元素可能和"停止"按钮同时出现，被误当成旧消息 | 点发送前先记下已有的消息 |
| 找按钮用的 `取消` 过宽，匹配到了侧边栏的"取消置顶聊天" | 所有标签改为完全匹配，侧边栏（`nav`、`aside`）里的按钮一律不点。之后检查，置顶聊天还在 |

**手机网页上的听写按钮（中文界面）。** 点"听写"之后，会出现"取消听写""停止听写""转录并发送"三个按钮；输入框有文字后出现"发送"。

**结果：**

| 场景 | 结果 |
|---|---|
| Mac 上的模拟页（CSP 与真网站同类） | 通过。7 秒样本被模拟页的录音完整录下（7.3 s，峰值 -4 dB）；停止后 2.2 s 出现第一行回复，9.7 s 全部完成；356 字分 3 页，翻页正常 |
| 手机，真 chatgpt.com，样本音频实时喂入，不发送 | 转写和原文逐字一致，转写接口 747 ms |
| 手机，真 chatgpt.com，Firefox 在前台，用眼镜说话 | 通过。眼镜说"是测试"，转写为"是测试。"，自动发送；停止说话后 4.6 s 眼镜上出现回复，6.2 s 完成 |
| Even App 在前台，Firefox 在后台 | 失败："page did not open the mic after the dictation click"。点击发生了，但后台标签页没有打开麦克风 |
| 手机锁屏 | 失败 |

模拟器里中文、`■`、`•`、编号和表格都能显示。按校准结果，一行放 24 个汉字或 50 个数字，一屏 10 行；所以留 1 行状态加 9 行正文，宽度预算 48 个单位（汉字算 2）。眼镜实机上 `■` 和 `•` 能否显示还没有单独确认。回复里的 emoji（比如 🐺）多半会被固件丢掉。

测试中还发现两个原型自身的 bug，已在 0.4.3 版修好但还没有在手机上复测：

- 先长按再轻点会启动两个计时器，漏掉的那个在 60 秒后每 500 ms 发一次"停止"；
- 上一轮没关掉的听写会挡住"听写"按钮，导致后面连续报 "dictation button not found"。

结论：整条链路在技术上是通的，前台时延迟大约 5–6 秒。Firefox 一旦到后台或锁屏就完全不工作，而这正是戴着眼镜时的常态。这说明用 Firefox 加扩展只能当验证工具，最终需要独立的 GeckoView App：用前台服务保活，让 GeckoSession 在不可见时也保持活动状态。App 里还要验证，页面在不可见时 chatgpt.com 是否仍会打开麦克风。

### 独立 App：GeckoView 版 G2 Relay（2026-11-08，前台、后台、锁屏都通过）

把原型搬进一个独立的 Android App（源码在 `android/`，用 `scripts/android.sh` 构建和安装）：

- **浏览器**：GeckoView 159，只开一个 chatgpt.com 页面，登录状态保存在 App 自己的配置目录里。
- **页面脚本**：Firefox 原型的扩展脚本原样打包成内置扩展。
- **中转**：`broker.py` 改写成 App 里的 WebSocket 服务，监听 `127.0.0.1:8777`，不再需要 Mac 和 `adb reverse`。
- **保活**：前台服务加 CPU 唤醒锁和 Wi-Fi 锁。浏览器会话归 App 所有，界面退到后台时仍保持活动；界面只在可见时挂上。
- **音频**：允许自动播放，页面不用再点一下；手机的真实麦克风权限一律拒绝。

**遇到的问题：**

| 问题 | 处理 |
|---|---|
| GeckoView 159 要求 compileSdk 37.2，并带来 Kotlin 2.4 的标准库；AGP 9.5.1 内置的 Kotlin 2.2 读不了 | compileSdk 用 37.2（targetSdk 仍是 36），Kotlin 插件指定 2.4.21 |
| Android 上 `InetAddress.getLoopbackAddress()` 返回 `::1`，扩展连 `127.0.0.1` 被拒 | 明确绑定 `127.0.0.1` |
| 手机上的 Firefox 原型扩展也连同一个端口，会变成第二个"页面" | 只接受 App 自己内置扩展的来源（`moz-extension://<uuid>`） |

**结果（Galaxy Z Fold5，Android 14，用眼镜说话，每次都真实发送）：**

| 场景 | 停止说话 → 首行回复 | 停止说话 → 回复完成 | 转写接口 |
|---|---|---|---|
| Even App 在前台，G2 Relay 在后台 | 5.2 s | 6.6 s | 621 ms |
| 锁屏（屏幕关闭） | 4.7 s | 7.3 s | 773 ms |
| G2 Relay 在前台 | 3.9 s | 7.8 s | 799 ms |

三次都在眼镜上收到完整回复，前后台和锁屏的状态由系统事件日志核对过。锁屏时 Even 插件也照常采音（7.0 s 音频在 7.5 s 内送达），所以 Firefox 时期的后台失败，是 Firefox 把后台标签页停掉造成的，chatgpt.com 本身不拒绝页面不可见时听写。

**还没做：**

- 长时间待机（几十分钟以上、进入深度休眠）后是否还能用；
- 电池优化豁免对待机的影响；
- 耗电；
- 聊天中转插件已打包成私有 beta 0.1.0（`com.g2codeterminal.chatrelay`，源码在 `plugin/`），但还没在脱离 Mac 的情况下实测；
- 眼镜实机上 `■`、`•` 的显示。
